# Form Content Service

Managing Semantic Form instances. These instances are created from a form-definition. These definitions can be static or controlled by the end-user.

## Getting started

### Local development

#### Docker image

1. Build an image from the Dockerfile (e.g. `local-form-content`)
2. Run the container in development

```bash
docker run --rm -it -p 9229:9229 -p 8081:80 -e NODE_ENV=development local-form-content
```

3. Running it in development mode and exposing port 9229 allows you to connect your debugger to the docker.

#### Debug Compose

This file is available for convenience while developing, it has sane defaults for connecting it to the app-lokaal-mandatenbeheer docker-compose setup where it was conceived. Take note that this depends on your app connecting its database and dispatcher to the debug network as well as to its default network.

### Packages

This service works best in combination with the [`ember-semantic-forms`](https://github.com/lblod/ember-semantic-forms) addon. This will help with visualization of forms. For working with fully generated forms **Lokaal Mandatenbeheer** has added a custom-form-builder to it's application where a user can create a form from scratch [`<EditableForm/>`](https://github.com/lblod/frontend-lokaal-mandatenbeheer/blob/master/app/components/editable-form.js).

### Project Structure

- Routing and anything Express related resides in `/controllers`. The routes should be simple methods that call services.
- Services reside in `/services`. This is where the business logic and validations are.
- Queries for the database or Comunica go in `/domain/data-access`. These query methods should only contain the means to query or mutate the data, and return the result in a format that the service understands.
- Helpers reside in `/helpers` and contain functionality that is used in multiple services or queries.

## Requirements

Running the service standalone will not give you a working setup. The following are prerequisites:

- **The `/config` directory mount is mandatory.** At startup the service calls `fs.readdir('/config')` and loads `<name>/form.ttl` (plus an optional `<name>/meta.ttl`) for every directory found. If any file is missing or invalid, `loadFormsFromConfig()` throws and the container exits. `docker-compose.debug.yml` mounts `../app-lokaal-mandatenbeheer/config/form-content` on `/config`; a minimal setup is:

  ```yaml
  form-content:
    image: semtech/mu-javascript-template:1.9.1
    environment:
      - NODE_ENV=development
    labels:
      - 'logging=true'
    links:
      - db:database
      - identifier:identifier
    volumes:
      - ./config:/config
      - ./:/app
  ```

- **mu-identifier (and a session):** every write reads the `mu-session-id` request header and returns `401 Not authenticated` when no logged-in user can be resolved from it.
- **mu-auth:** updates and deletes go through the user's session and therefore through mu-auth, so the user needs write access to the graph of the instance. History snapshots are written with `updateSudo`, so `http://mu.semte.ch/graphs/formHistory` must be writable for the sudo account.
- **A triplestore (Virtuoso):** the bundled `mu` library queries Virtuoso through mu-authorization, and the CONSTRUCT used to read instances avoids `UNION` because it is broken in Comunica (see `form-validator.ts`).
- **Routing:** add `dispatcher.ex` rules for the paths you expose; nothing is routed automatically.

A smoke test once the stack is up, assuming the service is exposed directly on 8080 (don't do this in an actual deployment, go through the identifier+dispatcher):

```bash
curl http://localhost:8080/                        # {"status":"ok"} through the dispatcher
curl -H 'mu-session-id: <session-uri>' http://localhost:8080/forms   # list loaded config directories
```

### Listing query parameters

- `page[size]` (default **10**, also used by the history endpoints) and `page[number]` (default 0, converted to an offset). `limit` and `offset` are **not** read.
- `sort`: a label variable name, e.g. the lowercased label without whitespace (`var` in the response). Prefix with `-` for descending. Defaults to sorting on `uri`.
- `filter`: case-insensitive substring match against the label predicates only. The count and the list endpoints apply the same filter, so filtering on a non-label predicate is not possible.
- `labels`: URL-encoded JSON array of label objects (`{ name, var, order?, uri?, type? }`) used to select and order the returned columns. These are display labels, matched on `var`, not URIs. When omitted, the form's own summary labels are used.

Each instance in `instances` looks like `{ uri, id, <labelName>: value, ... }` where the label names are the `sh:name`s of the selected labels. Values for the `custom-date-input` and `custom-address-input` display types are formatted for display.

## Model

This service follows the semantic forms model and to that end uses the [ember-semantic-forms](https://github.com/lblod/ember-semantic-forms) package. However, some extensions are needed and they may not have made it into the form spec yet. The main extensions are: listing form instance, defining the uri prefix for form instances, linking to other types (possibly forms) using dropdowns etc.

### Form definition conventions

Listing and reading instances only works when the definition follows these conventions:

- The form must declare `form:targetType`; without it listings fail with `Unsupported Form: did not specify target type`.
- The predicate in `form:targetLabel` must also be the `sh:path` of a field that is part of the form (`form:includes`), otherwise you get `no valid target label supplied`.
- Every instance must carry a `mu:uuid` next to the target type. If the form defines a `form:Generator`, generate it with `form:dataGenerator form:addMuUuid`. The nested-field example below needs a type and a UUID on the nested node for exactly this reason: trimming and listing only keep paths whose intermediate nodes have both.
- The service stamps `dcterms:modified` on every instance on create and update. Only properties covered by the form's field paths and generator paths are stored.
- The service is tolerant of missing optional properties, but a form definition without `sh:group` has no group to add new fields to (see `Types of forms`).

### Listing Form Instances

Listing of form instances is done based on a the form definition. The form definition specifies the type of instances it acts on and the way these instances are to be rendered using `form:targetType` and `form:targetLabel` respectively. The targetLabel specifies the predicate to be used to fetch a label to use when rendering the form instance. In the future this can be extended to multiple paths to render different labels. Form instances are paginated, with a default of 10 instances per page. Pagination is controlled through the `page[number]` and `page[size]` query parameters. The total number of instances is returned in the `X-Total-Count` header. See [Listing query parameters](#listing-query-parameters) for sorting and filtering.

Which columns are shown by default is driven by `form:showInSummary true` on the fields. If no field has it, the service falls back to the field matching `form:targetLabel`. The summary labels are also the ones used by `POST /instances/by-form-definition-uri` to build its searchable label list.

### Defining the URI prefix for form instances

The URI prefix of a form instance can be specified in the form.ttl file. This can be done by adding a triple of the following form: `ext:form ext:prefix <prefix>`. The prefix is a variable and should be an IRI (a plain string will not be resolved), but otherwise there are no restrictions. If it does not end in `/` or `#`, one is appended. If no prefix is defined, the following prefix will be used by default: `https://data.lblod.info/form-data/instances/`.

The prefix and the instance id are two different things: the instance URI is chosen by the client (typically `<prefix><uuid>`), while the instance id is the value of `mu:uuid` on the instance. The API uses the UUID, not the URI, e.g. in `/:formId/instances/:instanceId`.

### Links to other types

Links to instances of another type are created through fields with a special display type. Supported mechanisms:

- `http://lblod.data.gift/display-types/lmb/custom-link-to-form-selector-input` requires the field to define `ext:linkedFormType <targetFormUri>`; the client then offers instances of that form. The validation of `POST /custom-form/field/is-uri-allowed-as-path` and `GET /definition/:id/used-in-custom-form-configuration` rely on the same predicate to detect where a form is used.
- Concept-scheme backed selectors (e.g. `custom-concept-scheme-selector-input`) require `fieldOption:conceptScheme <schemeUri>` on the field. These are the field types the service validates when a field is added or updated.
- Reusable fields can be copied from a library entry (`ext:FormLibraryEntry`). The copied field is marked with `ext:isLibraryEntryField` and linked to its source with `prov:wasDerivedFrom`.

Fields on generated forms that were given an explicit path by the user (instead of the generated one) are marked with `ext:hasUserInputPath`. When a form is extended, the added fields are marked with `ext:isExtensionField`.


### Nested Fields

In case of nested fields, e.g.

```
ext:geboorteF
    a form:Field;
    form:displayType displayTypes:dateTime;
    sh:group ext:persoonPG;
    sh:name "Geboortedatum";
    sh:order 6;
    sh:path ( persoon:heeftGeboorte persoon:datum ).
```

The corresponding form:Generator should be modified to also generate a type and UUID for the nested field, as otherwise the data would not be processable by mu-auth and resources respectively:

```
ext:personG a form:Generator;
  form:prototype [
    form:shape [
      a person:Person;
      persoon:heeftGeboorte [
        a persoon:Geboorte
      ]
    ]
  ];
  form:dataGenerator form:addMuUuid.
```

### Meta data and concept schemes

When a form's fields reference a concept scheme (through `form:options` JSON with a `conceptScheme` key), the service loads the concept and scheme triples from the triplestore and returns them in the definition's `metaTtl`, next to `formTtl`. For forms from `/config`, the contents of an optional `meta.ttl` file in the same directory are included as well.

### Deleting form instances

When a form instance is deleted, a [tombstone](https://www.stevebate.net/ontologies/activitystreams2/class-astombstone.html) is erected for every uri where a triple was removed that expresses the type for that uri. E.g. if on delete of a form instance, the following triple is removed

```
ext:1 a foaf:Person .
```

Then the following data is inserted in the store:

```
ext:1 a as:Tombstone ;
        as:formerType foaf:Person ;
        as:deleted "thetimeofdelete"^^xsd:dateTime  .
```

## Tracking history

Form definitions can specify that their history should be tracked by adding a triple `<formDefinitionUri> ext:withHistory "true"^^xsd:boolean`. When an instance of such a form is created or updated, the new triples of the form instance after that operation are written to a **new graph** with an auto-generated uri, e.g. `<http://mu.semte.ch/graphs/formHistory/d420c907-8bbd-4f5b-b89c-be330df247ea>`. Let's call the URI of this graph the historyInstanceUri. At the end of this operation, that graph contains all triples that would normally be returned when fetching the form instance using the form definition used to update it.

Meta information about this update is written to a specific graph `<http://mu.semte.ch/graphs/formHistory>`. This meta information describes the historyInstanceUri and is made up of the following triples:

```
@prefix dc: <http://purl.org/dc/elements/1.1/>.
@prefix dct: <http://purl.org/dc/terms/>.
@prefix xsd: <http://www.w3.org/2001/XMLSchema#>.
@prefix ext: <http://mu.semte.ch/vocabularies/ext/>.

<historyInstanceUri> a ext:FormHistory ;
                      dct:isVersionOf <formInstanceUri> ;
                      dct:issued "2024-03-12T12:29:00.000Z"^^xsd:dateTime ;
                      dct:creator <uriOfCreatorUser> ;
                      dct:description "updated the name of the organization" .
```

In this data, the graph containing the history information is used as the subject. It refers to the form instance it's a history entry of using `dct:isVersionOf`. The time at which the version was created is stored using `dct:issued`. The user that created the instance can be found by following the `dct:creator` predicate. Finally, a `dct:description` can be provided (optionally) that contains a free form text description of the change.

The service writes history automatically in these cases:

- On creation of an instance, with the description `Created`.
- On the first `PUT` of an instance that has no history yet, a snapshot of the **original** state is written first, with the description `Originele versie`. The updated state is then written as a second entry using the description passed in the request body.
- Whenever a description is passed in `PUT` or `POST /:formId/instances/:instanceId/history`, a snapshot is written with that description.

The service does **not** record which form definition produced a history item, so a consumer cannot tell from the history entry which form was used.

> [!CAUTION]
> Careful: a form instance can possibly be updated through different form definitions, each with their own fields. A history item will ONLY keep track of the properties that are controlled by the form definition that was used to create the item. E.g. if you have a form that controls only the end date of an event and a form that controls all properties of the event (e.g. name), the history item linked to updating only the end date through the specialized form will only contain the triples related to the end date and NOT the name. If you'd want to restore such an item, you'd have to restore the version of the item from before the end time update (if any) and then restore the triples referring only to the end time.

### Reading history

History is read with elevated permissions (`querySudo`), because the history graphs are not visible to end users, but access is checked explicitly first:

- `GET /:formId/instances/:instanceId/history` returns `{ instances: [] }` and count 0 when the user has no access to the instance. The list is ordered by `dct:issued`, newest first.
- `GET /history?historyUri=` checks access to the instance the snapshot belongs to. If access is denied it returns HTTP 200 with a `null` body instead of a `403` or `404`. This is to avoid giving the user information on instances that it doesn't have access to, like is done in mu-authorization by default.

## Types of forms

There are three different type of forms that this service is able to manage. Every type of form needs the correct structure so the service known how to manage every one of them. Instances can be created for every type of form.

1. Forms (1\*)

These forms work with a static form-definition that lives in the config folder. A form definition folder structure can be as followed with form.ttl

```md
--|config
|--| my-form
|-- form.ttl
|-- meta.ttl (optional)
```

2. Form **extensions**

These forms work with a base static form-definition which can be extended by the end-user with other fields. A form definition folder structure can be as followed with form.ttl

```md
--|config
|--| my-form-extension
|-- form.ttl
```

3. **Generated** forms

These forms can be created by using the available endpoints. If you want a more in depth look on how these forms are buildup you can have a look at `form-definitions.ts` method `createEmptyFormDefinition()`

Generated and extended forms are not stored on disk. They live in the triplestore as `ext:GeneratedForm` with their turtle source in `ext:ttlCode`, and are flagged with `ext:isCustomForm`. Only static forms and static extensions are loaded from `/config`. The in-memory registry of `/config` forms is only refreshed on restart.

> Note: when a path is not specified when adding fields they get a generated path

> [!WARNING]
> complex paths are broken at the moment, this means that if the sh:path object is a class value it won't set the value correctly!

> Note: fields added to a form are placed in the first `form:PropertyGroup` or `form:FieldGroup` found in the form definition; the service does not support choosing a group per field.

## Extending Forms

### Predicates and Types

Use the same model as regular forms, with the following differences:

- To connect a field/section to a section of the owning form, use `ext:extendsGroup` instead of `sh:group`.
- If you want to introduce a new section in your extension, still use `sh:group`.
- Use `ext:extendsForm` to connect to the URI of the form being extended.

An extension (type: `form:Extension`) is represented by

```
<extensionUri> a form:Extension ;
                form:includes <fieldUri> ;
                ext:extendsForm <formUri> ;
                mu:uuid "b5a86f3a-aac8-4911-a3fb-37f9f194b58e" .
```

Note that if you want to add a field to an existing Section, there is no need to define that section again using a `sh:group` from the extension to the section. This link is already specified in the original form. You only need to add a link like this for entirely new sections that you create.

### Order

We want fields to be added to the original form in a specific order, intermixed with the existing fields (before, after, between). Unfortunately, the order property is an integer and loses float/double precision if it is added to it. Therefore we should leave gaps of e.g. 100 between the order properties of our forms.

### Editing a standard form

Adding a field (`POST /:formId/fields`), or updating one (`PUT /:formId/fields`), on a **standard** form does not change the form from `/config`. The service creates a new `form:Extension` with `ext:isCustomForm true`, links it to the original with `ext:replacesForm`, and returns the extension. The response of `POST /:formId/fields` therefore describes the new extension, not the original form. `GET /form-replacements` lists all such standard-to-extension links.

### Extending the form with direct properties

In an extension, we should be able to specify the same direct properties that we use in a regular form. In that case, we should define them on the `form:Extension`, instead of on the `form:Form`, using the same predicates as the ones used on the `form:Form`. The form-content service will take the `form:Extension` instance and transform it into a `form:Form` instance that contains the combination of the new properties and the properties that exist on the form that is being extended. The properties `form:targetType`, `form:targetLabel` and `ext:prefix`, can be reconfigured, if they are defined in the form extension, this new value is used. If they are not defined in the extension, the ones value the base form is used. The property `mu:uuid` should be defined in the form extension and the old value overwritten. Other properties are taken from both, and are combined.

### Transparency of `form:Extension`s

To clients of the form-content service, instances of the `form:Extension` class will be presented as instances of the `form:Form` class. To the client, the only difference is the existence of the extra `form:Extension` class, which they should be able to ignore.

### Recursive Extension

Because a form extension is translated directly into a regular form, it is straight forward to create an extension of an extension. In that case, the `ext:extendsForm` predicate points to the URI of another `form:Extension`. The translation to a form follows the following algorithm:

```
def form_to_fetch(uri):
  if is_extension(uri):
    base = get_extended(uri)          # follows ext:extendsForm
    return merge_into_form(form_to_fetch(base), uri)
  else:
    return uri
```

The implementation (`extendForm` in `services/form-extensions.ts`) resolves the base form first, recursively, and then merges the extension on top. This handles chains of extensions, but there is **no cycle detection**: an `ext:extendsForm` loop will recurse until the process runs out of stack. These are normally not created by the system but it's worth pointing this out.

## Limitations

### No Generator Shape Paths

Currently, this service only supports generators with simple paths and with nested types in their shape, e.g.

```
ext:mandatarisG a form:Generator;
  form:prototype [
    form:shape [
      a ns:Mandataris
    ]
  ];
  form:dataGenerator form:addMuUuid.
```

and

```
ext:personG a form:Generator;
  form:prototype [
    form:shape [
      a person:Person;
      persoon:heeftGeboorte [
        a persoon:Geboorte
      ]
    ]
  ];
  form:dataGenerator form:addMuUuid.
```

This generator's shape only has direct attributes (a ns:Mandataris) and nested types without modifiers, like sh:inversePath. Anything more complicated will not be handled by this service yet.

For instance, this shape is **not supported**:

```
ext:mandatarisG a form:Generator;
  form:prototype [
    form:shape [
      a ns:Mandataris
      mandaat:isBestuurlijkeAliasVan / foaf:name "De Grote Smurf"
    ]
  ];
  form:dataGenerator form:addMuUuid.
```

### No Modified Simple Paths in fields or generator scopes

Fields and Generators can each define a scope. This service supports simple paths (e.g. `foaf:name`) and complex paths (e.g. `( [ sh:inversePath mandaat:isAangesteldAls ] foaf:name )`). However, modified simple paths are **not supported** (e.g. `[ sh:inversePath mandaat:isAangesteldAls ]`). Luckily, these can always be written in their complex form, which IS supported: `( [ sh:inversePath mandaat:isAangesteldAls ] )` (note the wrapping brackets in this case, signifying a linked list in RDF).

### Lenient Form Validity Checks

The validity of all forms is checked at startup, but the parsing library that we currently use (N3) is lenient and will sometimes still parse a form, even if it uses unknown prefixes. Therefore the full validity of the forms at runtime cannot be guaranteed, they just pass through a best effort check.
